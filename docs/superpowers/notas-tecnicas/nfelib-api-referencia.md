## 1. Estrutura de diretórios relevante

`nfelib` empacota bindings para vários documentos fiscais brasileiros
(`nfe`, `cte`, `mdfe`, `bpe`, `nfse`, e vários sub-schemas de eventos).
Para NF-e **e NFC-e** (são o mesmo schema — ver seção 2), o caminho é:

```
nfelib/nfe/bindings/v4_0/
├── __init__.py                      # re-exporta as classes públicas
├── nfe_v4_00.py                     # classe raiz `Nfe`
├── proc_nfe_v4_00.py                # classe raiz `NfeProc` (doc + protocolo)
├── leiaute_nfe_v4_00.py             # 11749 linhas — TODAS as classes de conteúdo
│                                      (Tnfe, Ide, Emit, Dest, Det, Prod,
│                                      Imposto, Total, Pag, etc., como
│                                      classes aninhadas)
├── dfe_tipos_basicos_v1_00.py       # 2252 linhas — tipos compartilhados de
│                                      reforma tributária (TtribNfe, Tcibs,
│                                      Tmonofasia, TibscbsmonoTot, etc.)
├── tipos_basico_v4_00.py            # enums básicos (Tmod, Tamb, TcodUfIbge, ...)
├── envi_nfe_v4_00.py, ret_envi_nfe_v4_00.py, cons_sit_nfe_v4_00.py, ...
│                                      # lote de envio / consulta de situação
└── xmldsig_core_schema_v1_01.py     # binding do XML-DSig (assinatura)
```

Isto bate **exatamente** com o caminho hipotético do brief
(`nfe/bindings/v4_0/`).

O cabeçalho de `leiaute_nfe_v4_00.py` diz:
```

Generator: DataclassGenerator
```

## 2. NFC-e NÃO é um pacote/módulo separado

Não existe `nfelib/ncfe` nem `nfelib/nfce`. NF-e e NFC-e compartilham o
mesmo XSD/schema `nfe_v4.00.xsd` e a mesma árvore de classes Python. A
diferenciação é feita por um campo, não por uma classe:

```python
# Tnfe.InfNfe.Ide.mod  -> tipo Tmod (enum)
class Tmod(Enum):
    VALUE_55 = "55"   # NF-e
    VALUE_65 = "65"   # NFC-e
```
(`tipos_basico_v4_00.py`, confirmado por leitura direta e por
`ide.mod == Tmod.VALUE_55` observado no teste de round-trip da seção 6).

Para emitir NFC-e usa-se **a mesma classe `Nfe`**, preenchendo
`ide.mod = Tmod.VALUE_65`.

## 3. Import da classe raiz

```python
from nfelib.nfe.bindings.v4_0 import Nfe, NfeProc
```

Confirmado lendo `nfelib/nfe/bindings/v4_0/__init__.py`:
```python
from nfelib.nfe.bindings.v4_0.nfe_v4_00 import Nfe
from nfelib.nfe.bindings.v4_0.proc_nfe_v4_00 import NfeProc
```

- **`Nfe`** (`nfe_v4_00.py`) — é o documento "puro" (`<NFe>`), herda de
  `Tnfe` e define `Meta.name = "NFe"`,
  `Meta.namespace = "http://www.portalfiscal.inf.br/nfe"`. É esta classe
  que se deve instanciar para **construir e assinar** uma NF-e/NFC-e.
- **`NfeProc`** (`proc_nfe_v4_00.py`) — é o documento processado
  (`<nfeProc>`), herda de `TnfeProc` (de `leiaute_nfe_v4_00.py`) e
  contém `.NFe` (o documento assinado) + `.protNFe` (o protocolo de
  autorização devolvido pela Sefaz). Útil para **ler** uma NFC-e já
  autorizada (ex.: reimprimir, consultar).

O corpo real do documento (`Tnfe`) fica em `leiaute_nfe_v4_00.py`, com
toda a estrutura de dados como **classes aninhadas dentro de
`Tnfe.InfNfe`** — isto é atípico em relação a bibliotecas "flat" e é
importante que as próximas tasks saibam disso, porque os nomes de
import corretos são caminhos como `Tnfe.InfNfe.Ide`, não `Ide` solto:

```python
Tnfe.InfNfe          # nfelib.nfe.bindings.v4_0.leiaute_nfe_v4_00.Tnfe.InfNfe
Tnfe.InfNfe.Ide
Tnfe.InfNfe.Emit
Tnfe.InfNfe.Dest
Tnfe.InfNfe.Det
Tnfe.InfNfe.Det.Prod
Tnfe.InfNfe.Det.Imposto
Tnfe.InfNfe.Total
Tnfe.InfNfe.Total.Icmstot
Tnfe.InfNfe.Pag
Tnfe.InfNfe.Pag.DetPag
```

Na prática, ao instanciar, não é preciso importar cada classe aninhada
individualmente por um caminho longo — basta importar `Nfe` e construir
de fora para dentro, referenciando os tipos aninhados via
`Nfe.InfNfe.Ide(...)` etc., OU importar diretamente
`from nfelib.nfe.bindings.v4_0.leiaute_nfe_v4_00 import Tnfe` e usar
`Tnfe.InfNfe.Ide(...)`. Ambas as formas funcionam (dataclasses Python
comuns).

## 5. `emit` — Emitente (`Tnfe.InfNfe.Emit`)

Campos: `CNPJ`/`CPF` (um dos dois), `xNome` (obrigatório), `xFant`,
`enderEmit: TenderEmi` (obrigatório), `IE` (obrigatório),
`IEST`, `IM`, `CNAE`, `CRT: EmitCrt` (obrigatório — regime tributário:
1 Simples, 2 Simples excesso sublimite, 3 Normal, 4 MEI).

## 6. `dest` — Destinatário (`Tnfe.InfNfe.Dest`)

Todo o grupo `dest` em si é **opcional** em `InfNfe` (`dest:
Optional["Tnfe.InfNfe.Dest"]`, sem `required=True`) — coerente com
NFC-e ao consumidor final sem CPF/CNPJ informado. Dentro dele:
`CNPJ`, `CPF`, `idEstrangeiro`, `xNome`, `enderDest: Tendereco`,
`indIEDest: DestIndIedest` (**obrigatório** quando o grupo existe),
`IE`, `ISUF`, `IM`, `email`.

## 7. `det` / item (`Tnfe.InfNfe.Det`)

`det` é uma lista (`List["Tnfe.InfNfe.Det"]`, `min_occurs=1,
max_occurs=990`) com atributo `nItem` obrigatório. Cada item tem:
`prod` (obrigatório), `imposto` (obrigatório), `impostoDevol`,
`infAdProd`, `obsItem`, `vItem`, `DFeReferenciado`.

### 7.1 `Tnfe.InfNfe.Det.Prod`

Campos obrigatórios confirmados: `cProd`, `cEAN` (aceita a string
literal `"SEM GTIN"`), `xProd`, `NCM`, `CFOP`, `uCom`, `qCom`, `vUnCom`,
`vProd`. Campos de reforma tributária presentes aqui também:
`cBenef`, `gCred: List[Prod.GCred]` (crédito presumido — até 4
ocorrências), `tpCredPresIBSZFM: TtpCredPresIbszfm` (classificação de
subapuração do crédito presumido na Zona Franca de Manaus).

### 7.2 `Tnfe.InfNfe.Det.Imposto`

## 8. O grupo IBS/CBS em detalhe — `TtribNfe` (`dfe_tipos_basicos_v1_00.py`)

```python
@dataclass
class TtribNfe:
    CST: Optional[str]                       # obrigatório, \d{3}
    cClassTrib: Optional[str]                # obrigatório, \d{6}
    indDoacao: Optional[TindDoacao]
    gIBSCBS: Optional[Tcibs]                 # tributação "normal"
    gIBSCBSMono: Optional[Tmonofasia]        # tributação monofásica (CST 620)
    gTransfCred: Optional[TtransfCred]       # CST 800 (transferência de crédito)
    gAjusteCompet: Optional[TajusteCompet]   # CST 811
    gEstornoCred: Optional[TestornoCred]
    gCredPresOper: Optional[TcredPresOper]
    gCredPresIBSZFM: Optional[TcredPresIbszfm]
```

Todos exceto `CST` e `cClassTrib` são opcionais — a escolha de qual
sub-grupo preencher depende do valor de `cClassTrib` (classificação
tributária de 6 dígitos definida pela reforma).

## 11. Serialização — método real confirmado

Todas as classes de conteúdo (`Tnfe`, `TprotNfe`, `TnfeProc`, etc.)
herdam de **`nfelib.CommonMixin`** (`nfelib/__init__.py`), que expõe:

```python
class CommonMixin:
    @classmethod
    def from_xml(cls, xml: str, config: ParserConfig = None) -> Any: ...
    @classmethod
    def from_path(cls, path: str) -> Any: ...
    @classmethod
    def schema_validation(cls, xml: str, schema_path: Optional[str] = None) -> list: ...
    @classmethod
    def sign_xml(cls, xml: str, pkcs12_data=None, pkcs12_password=None, doc_id=None) -> str: ...
    def to_xml(self, indent="  ", ns_map=None, pkcs12_data=None,
               pkcs12_password=None, doc_id=None, pretty_print=None) -> str: ...
    def validate_xml(self, schema_path: Optional[str] = None) -> list: ...
    def to_pdf(self, engine="brazilfiscalreport", config=None,
               pkcs12_data=None, pkcs12_password=None, doc_id=None) -> bytes: ...
```

Por baixo, `to_xml()` usa **`xsdata.formats.dataclass.serializers.XmlSerializer`**
com `SerializerConfig(indent=...)`, exatamente como o brief previu como
alternativa. Não existe um `.to_xml()` mais simples/separado — este é
o método real e único.

Ponto crítico: **`to_xml()` já sabe assinar** — se você passar
`pkcs12_data`/`pkcs12_password` (bytes do .pfx e senha), ele chama
internamente `cls.sign_xml(...)`, que por sua vez faz:

```python
from erpbrasil.assinatura import certificado as cert
from erpbrasil.assinatura.assinatura import Assinatura
certificate = cert.Certificado(arquivo=pkcs12_data, senha=pkcs12_password)
xml_etree = etree.fromstring(xml.encode("utf-8"))
return Assinatura(certificate).assina_xml2(xml_etree, doc_id)
```

Ou seja, **`nfelib` já integra `erpbrasil.assinatura` nativamente** —
confirma que essa é de fato a biblioteca de assinatura "esperada" pelo
ecossistema, como o brief alertou para não substituir por outra.

Assinaturas reais confirmadas por introspecção (`inspect.signature`):
```python
erpbrasil.assinatura.certificado.Certificado.__init__(self, arquivo, senha, raise_expirado=True)
erpbrasil.assinatura.assinatura.Assinatura.assina_xml2(self, xml_element, reference, getchildren=False)
```

## 12. Teste real de round-trip (executado neste ambiente)

O pacote distribui um XML de amostra **já com IBS/CBS preenchido**, em:
```
nfelib/nfe/samples/v4_0/leiauteNFe/nfe_reforma_tributaria.xml
```
(caminho completo:
`C:\laragon\bin\python\python-3.13\Lib\site-packages\nfelib\nfe\samples\v4_0\leiauteNFe\nfe_reforma_tributaria.xml`)

Executei o parse + reconstrução + serialização:

```python
from nfelib.nfe.bindings.v4_0 import NfeProc, Nfe

proc = NfeProc.from_path(".../nfe_reforma_tributaria.xml")
ide = proc.NFe.infNFe.ide
# ide.mod == Tmod.VALUE_55, ide.tpAmb == Tamb.VALUE_1, ide.nNF == 664350

imposto = proc.NFe.infNFe.det[0].imposto
ibscbs = imposto.IBSCBS
# ibscbs.CST == "000", ibscbs.cClassTrib == "000001"
# ibscbs.gIBSCBS.vBC == "800", ibscbs.gIBSCBS.vIBS == "0"
# ibscbs.gIBSCBS.gCBS.vCBS == "101"

nfe = Nfe(infNFe=proc.NFe.infNFe, infNFeSupl=proc.NFe.infNFeSupl,
          signature=proc.NFe.signature)
xml_out = nfe.to_xml()
# xml_out começa com: <NFe xmlns="http://www.portalfiscal.inf.br/nfe">
# 'IBSCBS' in xml_out and 'vIBS' in xml_out  -> True, True
```

**Resultado: passou.** O parse reconhece corretamente os campos
IBS/CBS do XML de amostra (que é um XML de teste oficial do próprio
projeto `nfelib`, refletindo a NT da reforma), e a reserialização via
`Nfe(...).to_xml()` produz `<NFe xmlns="http://www.portalfiscal.inf.br/nfe">`
como elemento raiz com o conteúdo IBS/CBS preservado. Isto confirma
que a cadeia **parse → construir objeto → serializar** funciona de
ponta a ponta nesta versão instalada, incluindo os campos de reforma
tributária.

## 13. Outros achados úteis (não pedidos explicitamente, mas relevantes às próximas tasks)

- `nfelib/nfe/client/v4_0/servers.py` contém um dicionário de
  endpoints SOAP por UF/ambiente (autorização, consulta, distribuição,
  etc.) mas **não foi inspecionado a fundo** aqui — é escopo da task de
  cliente SOAP/webservice, não desta. Uma busca rápida por `"DF"` não
  encontrou uma chave dedicada de UF="DF"; a tabela usa agrupamentos
  como `"SVRS"`. A task que implementar a comunicação com o
  webservice da Sefaz-DF deve investigar isso especificamente — **não
  assumir aqui qual grupo/URL o DF usa**.
- `TprotNfe` / `TprotNfe.InfProt` (em `leiaute_nfe_v4_00.py`, linha
  ~1555) modela a resposta de protocolo da Sefaz: `tpAmb`, `verAplic`,
  `chNFe`, `dhRecbto`, `nProt`, `digVal`, `cStat`, `xMotivo`, `cMsg`,
  `xMsg`. Útil para a task que trata o retorno da autorização.
- `CommonMixin.to_pdf()` existe (DANFE), mas depende de um pacote
  externo opcional (`brazilfiscalreport` ou `erpbrasil.edoc.pdf`) que
  **não foi instalado/testado** nesta task — fora do escopo do plano
  atual (que usa `qrcode` diretamente, não DANFE completo).

   (confirmado por leitura de código e por teste de round-trip com XML
